# セルフコードレビュー記録（2026-11-10）

対象：lib/ 全13ファイル（約2,200行）。観点は正確性、状態遷移、ライフサイクル、
API応答の堅牢性、UIの溢れ、テストカバレッジ。修正したものには回帰テストを追加した
（test/regression_test.dart）。F1は修正前に戻すとテストが失敗することも確認済み。

## 修正した指摘

### F1スコア正規化の分母が規定ターン数固定で、先手が構造的に有利だった
- 箇所：`lib/services/mock_debate_engine.dart` judgeAndSummarize
- 内容：正規化の分母が `91 * (総ターン数/2)` 固定だった。早期決着や判定リクエストで
バトルが奇数ターンで終わると、先手（ひろゆき）だけ発言が1回多く、
同じ分母で割るため先手のスコアが構造的に高くなった。あわせて途中終了時は
全体スコアが下がる問題もあった。
- 修正：分母を各論客の「実際の発言ターン数」に変更。
- 回帰テスト：同じ質の発言を3ターン vs 2ターンで与え、同スコアになることを検証。

### F2判定JSONの winner が想定外でもひろゆき勝利になっていた
- 箇所：`lib/services/persona_prompts.dart` parseJudgeResult
- 内容：`winner == 'horiemon'` 以外はすべて hiroyuki に倒していたため、
AIが `"draw"` や日本語名を返した場合に黙ってひろゆき勝利になっていた。
- 修正：winner が `hiroyuki` / `horiemon` 以外なら null を返し、呼び出し側の
フォールバック（モック判定）に委ねる。
- 回帰テスト：想定外値・欠落で null、正常値と前後文字列付きJSONでパース成功。

### F3latestJudgeComment がバトル開始時にリセットされていなかった
- 箇所：`lib/state/debate_controller.dart`
- 修正：startBattle の初期化に追加（現状UI未使用だが状態の不整合として修正）。

### F4結果画面の合計バーが「値が100超なら400で割る」という暗黙ルールだった
- 箇所：`lib/screens/result_screen.dart`
- 修正：`_scoreRow` に `maxValue` 引数を追加し、カテゴリ=100／合計=400 を明示。

### F5お題に長さ制限がなく、対戦画面タイトルが長いお題で溢れ得た
- 箇所：`lib/screens/topic_screen.dart` / `battle_screen.dart`
- 修正：入力欄に maxLength 100（カウンタ非表示）。実AI時にお題はプロンプトへ
そのまま入るため、極端な長文の防止も兼ねる。タイトルは1行＋省略記号に変更。

## 修正しなかった指摘（判断理由つき）

- **http.Client を閉じていない**：エンジンはアプリ生存期間で単一インスタンスのため
実害なし。エンジンを画面ごとに生成する設計に変える場合は close の責務をセットで足すこと。
- **倍速切替が進行中の待機に即時反映されない**：`_wait` の残量は開始時点の速度で計算する。
最大でも1.5秒の待機の話であり、体感への影響は小さい。
- **APIキーは dart-define でバイナリに埋め込まれる**：配布バイナリから抽出可能。
個人利用の前提では許容するが、公開配布するならキーはサーバ側プロキシに移すこと。
README の注意にも追記した。
- **サイレントフォールバックの可観測性**：既知の課題として継続。エンジンの成否を
状態に持たせる改修は状態マシン設計の次のステップ（docs/state_machine_design.md 参照）。

# セルフコードレビュー第2回（2026-11-10、ロスター化直後）

対象：6人ロスター化で変更した全ファイル（モデル、モック／Gemini／OpenAIエンジン、
コントローラ、3画面、ウィジェット、pubspec）。

## 修正した指摘

### G1【小・堅牢性】実AIエンジンのペルソナ参照が強制アンラップだった
- 箇所：`gemini_debate_engine.dart` / `openai_debate_engine.dart` の nextTurn
- 内容：`PersonaPrompts.persona[speaker]!` のため、将来 DebaterId を追加して
  ペルソナ登録を忘れると、その論客のターンで例外になりバトルが止まる。
  「失敗しても止まらない」というエンジン全体のフォールバック方針と矛盾していた。
- 修正：ペルソナが引けない場合はモックのターンを返すよう変更（両エンジン）。

### G2【小・API安全性】BattleConfig が同一人物ペアを許していた
- 箇所：`lib/models/debate_models.dart`
- 内容：`first == second` の設定が作れてしまい、その場合 stanceOf／opponentOf が
  破綻したまま静かに動く。UI側では防いでいるが、モデル層の契約として弱かった。
- 修正：コンストラクタに `assert(first != second)` を追加（開発時に即検出）。

## 確認して問題なかった点

- 選択UIの割当ロジック（`_assign`）：4ケース（相手スロットの人を選択→入替、
  自スロットの人を選択→無変化、未選択の人→割当、割当後のアクティブスロット移動）
  をすべて追い、重複選択やペア喪失が起きないことを確認。UIテストでも担保済み。
- 判定まわり：`judgeSystemFor` が勝者候補を対戦ペアの enum 名に限定し、
  `parseJudgeResult` もペア外の勝者を null に倒すため、6人化しても
  「関係ない論客が勝者になる」ことはない。
- モック判定の一般化：勝者・敗者・スコアマップがペア基準になり、
  同点時は勢い側を勝者に倒す規則もペア非依存で維持されている。
- コントローラ：`_rawScores` は開始時にペア分だけ初期化され、エンジンが返す
  発言者は必ずペア内（モック／実AIとも nextSpeaker 基準）なので参照は安全。
- アセット：pubspec をディレクトリ指定に変えたため、今後のアバター追加で
  登録漏れが再発しない。

## 修正しなかった指摘（判断理由つき）

- **スコア倍率によるカテゴリ飽和**：得意カテゴリの倍率（例：マツコのユーモア
  ×1.3、ひろゆきの論理 ×1.15）では正規化前の値が分母（91/ターン）を超え、
  normalized の 100 クランプで頭打ちになる。高ロール同士の差が圧縮されるが、
  「得意分野では満点近くを取る」というキャラ表現として許容範囲と判断。
  バランス調整が必要になれば、分母を 91×最大倍率 に変えるのが候補。
- テスト総数：40件全通過（変更なし）。analyze クリーン、Webビルド成功。
